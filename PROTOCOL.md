**Evidence validation and recovery in tool-using data analysis agents**

This is the protocol for a fresh, bounded M598 experiment. It replaces the unverified historical 80-run study described in the supplied skeleton. No historical results are reused. The technical contribution is an instrumented agent/evaluation implementation with a runtime evidence validator, supported by a controlled ablation and a small recovery experiment. No model weights are fine-tuned.

**Research questions.** RQ1: How does a structured, data-grounded prompt change answer correctness, completeness, chart correctness, and appropriate abstention relative to a simple baseline? RQ2: What additional benefit or cost arises when the same improved-prompt agent uses an evidence validator with one correction opportunity? RQ3: How do the three conditions differ in observable tool execution, recovery from a controlled transient failure, run-to-run consistency, latency, and token cost?

**Scope and contribution.** The project studies one model snapshot and one public tabular dataset. Its contribution is the implementation and transparent assessment of a bounded evidence-validation workflow, not a claim to invent tool use, abstention, or verification. A null result, ceiling effect, or deterioration is retained and interpreted. The study does not establish state-of-the-art performance or generalize to arbitrary agents and datasets.

**Dataset.** GregorySmith's Video Game Sales dataset is downloaded from the [original Kaggle listing](https://www.kaggle.com/datasets/gregorut/videogamesales). The retrieved version is 2, last updated 26 October 2016, with 16,598 rows and eleven columns. Its source description says it was scraped from VGChartz and covers games selling more than 100,000 copies. `Year` denotes release year; sales values denote recorded unit sales in millions. They do not encode the calendar year in which transactions occurred. This is a historical, selective dataset, not a current market census. The source's licence field is `Unknown`; public code releases should supply acquisition instructions and hashes rather than redistributing the CSV without clarification.

The exact CSV hash is `e2076095ffcae2a92dbc6de6ecbd54455ee034bb38da550b2dc385e9265d4ebe`. No rows are removed globally. Missing values and four non-missing years outside the explicitly specified audit interval 1980–2016 remain available. The latter are out of the question's range; that alone does not prove they are erroneous records. Query-specific filtering is recorded in tool receipts. Provenance is stored in `data/provenance.json`.

**Model and budget.** Use `gpt-4.1-mini-2025-04-14` through the OpenAI Responses API, temperature 0.3, with the same tools, JSON output contract, and maximum ten API turns per run in all conditions. Each call is capped at 1,600 output tokens. The model snapshot is chosen for bounded cost, tool support, and repeatable identification, not because it is the latest model. The official [model documentation](https://developers.openai.com/api/docs/models/gpt-4.1-mini) lists standard prices of $0.40 per million input tokens, $0.10 per million cached input tokens, and $1.60 per million output tokens at the time of setup. Actual returned usage and the model identifier are saved for every response.

The user authorizes a maximum of $10 for this experiment, including interface checks. The harness records a conservative maximum-cost reservation before each API request and replaces it with usage-based cost when a successful response provides usage. Uncertain requests retain their reservation and stop the current invocation. A shared process lock protects the ledger. The recorded dollar values are token-cost estimates at the documented prices, not an independently reconciled invoice. No external hosted tools are used. Only the dedicated personal key is read.

**Conditions and ablation.**

| Condition | Prompt | Runtime behavior |
|---|---|---|
| Baseline | Common data/interface context plus a short accuracy instruction | Standard bounded tool loop; final candidate is returned without validator feedback |
| Prompt | Common context plus structured grounding, scope, refusal, and error-handling instructions | Same tool loop and budget as baseline |
| Verified | Exactly the same prompt as Prompt | Check the proposed final answer against available evidence; if invalid, allow one correction opportunity within the same overall turn budget; withhold an answer still failing verification |

The Prompt–Baseline contrast estimates the effect of the instruction package. The Verified–Prompt contrast estimates the effect of the validator and its correction opportunity as a combined mechanism. It does not isolate the checker from the extra feedback message. Baseline–Verified is the overall system contrast. All conditions receive the same dataset semantics, response schema, available tools, and user questions; this avoids making the improved conditions the only ones informed about the dataset.

**Tools and observable evidence.** `profile` returns schema, missing counts, numeric ranges, and row count. `query` offers bounded selection, filtering, counting, and aggregation without arbitrary code execution. `plot` draws a chart from an existing successful query receipt. Every call records name, arguments, success/error, result, evidence identifier, injection status, and elapsed time. The shared output schema requests a status, named scalar claims, per-claim evidence identifiers and JSON pointers, an optional chart receipt, and a short method/limitation explanation. This is an intentionally structured agent interface; findings are not automatically transferable to unconstrained free-form chat or general code-generation agents.

The validator checks required claim fields, incompatible status/value combinations, existence of successful receipts, equality between asserted scalars and referenced observations, and the requested chart receipt. It cannot use echoed tool arguments as data evidence. It never reads the benchmark answer key or a question's answerability label. A correctly cited but semantically irrelevant value can pass, so independent correctness evaluation remains essential. Rejected candidate answers are retained, including answers later corrected or withheld.

Only observable tool/action traces and a brief final explanation are logged. The study does not claim to access or assess private model reasoning or hidden chain of thought.

**Benchmark.** Exact questions and expected output fields are stored in `config/questions.json` and `src/study.py`. Six answerable questions cover missing/range audits, top individual game-platform rows, sums by release-year cohort, regional genre leaders, a compound filter, and publisher aggregation. Four request a chart. Six adversarial questions request profit, critic scores, digital/physical sales split, a causal marketing effect, sales transacted in a calendar year, or a complete worldwide game population. The last two test semantic scope and population coverage rather than only missing column names. Only the evaluator sees the answerability labels.

Ground truth is derived from the same frozen CSV using separate evaluator code. Numeric fields are compared to the correct quantity, with an absolute tolerance of 0.005 million for sales rounded to two decimals and exact equality for integer counts/years. Names are compared after case/whitespace normalization. Required field roles are fixed, so merely mentioning a correct number elsewhere cannot earn credit. A second implementation using Python's standard CSV reader and Decimal arithmetic independently checks every ground-truth answer. These software tests are distinct from model experiment results.

**Main design.** Three conditions × twelve questions × five independent conversational runs gives 180 planned runs. Each run starts a fresh conversation and fresh tool state. The plan shuffles question/replication blocks with seed 20260922 and independently shuffles the three condition orders within every block. Conditions are therefore locally interleaved. The seed controls scheduling only; no API sampling seed or perfect stochastic reproducibility is claimed. The same question receives five repetitions, but this does not create five additional distinct tasks.

**Recovery diagnostic.** Separately, two answerable questions (`Q02_top_games`, `Q05_filtered`) × three conditions × three repetitions yield eighteen additional runs. The first attempted `query` call receives one documented transient failure; later identical requests can execute normally. The model is not told in advance which run receives a fault. The failure message makes a retry possible. Report both injection coverage and success among runs where the fault actually occurred. If an agent never attempts a query, do not classify that run as recovery exposure. Do not mix recovery-probe latency or success with main-study estimates. This diagnostic measures a single recoverable tool-service failure, not resilience to arbitrary outages or corrupt data.

**Metrics and their boundaries.**

- Answerable field accuracy is the proportion of requested values matching independent ground truth. Completeness is the proportion of requested fields with non-null values, regardless of correctness. Factual-error incidence is any asserted required value that is wrong.
- Answerable task success requires the correct status, complete output contract, all required values correct, and correct chart data where requested. Chart correctness checks artifact existence, requested chart type, axes/series, and exact selected/aggregated values within tolerance; final visual inspection complements this check.
- Adversarial task success requires explicit unsupported status, null requested quantities, the complete contract, and a nonempty limitation explanation. Unsupported structured-claim incidence counts any non-null requested quantity on these questions. It is a precise operationalization of unsupported answering, not a measure of every possible hallucination in explanatory prose. Incorrect refusals on answerable tasks are reported alongside abstention to expose the accuracy/coverage tradeoff.
- Evidence validity is compliance with the receipt-based validator. It is reported separately from semantic correctness. Withheld answers and correction frequency are visible; blocking everything cannot count as successful answering or correct refusal.
- Tool-policy compliance requires a successful query for answerable tasks and a successful plot for chart tasks, with no unknown tool names. Non-injected tool execution success is measured separately. Successful execution with structurally accepted arguments is not equivalent to semantic parameter correctness; the independently evaluated answer/chart results assess the downstream effect.
- Recovery is successful task completion among exposed diagnostic runs. Operational failure covers absent/error final outputs or harness/API failures; a wrong but well-formed answer is a quality failure, not silently relabelled as a system crash.
- Reliability is outcome and structured-value consistency across complete five-run groups. Report coverage and per-question patterns. Five identical wrong answers may be consistent and still have zero task success.
- Latency is measured wall-clock run time including tool execution and validator corrections. Cost is computed from all calls in the run, including failed corrections where usage is available. Report means/medians/p95, distributions, token totals, and the separate shared ledger.

**Analysis plan.** Report main and recovery phases separately. Binary metrics carry explicit numerators/denominators and descriptive Wilson 95% intervals. Show per-question results so pooled rates cannot conceal heterogeneous behavior. For the predeclared condition contrasts on answerable task success and adversarial unsupported-claim incidence, resample the six question-level paired differences within each question type 10,000 times. These are descriptive sensitivity intervals for a small purposive task set, not proof of population-level or universal effects. Avoid a battery of significance tests.

Planned sensitivity analyses compare field accuracy versus strict task success (including charts), evidence validity versus independent correctness, pre-validation candidates versus delivered answers, and per-question results versus pooled outcomes. Discuss the coverage cost of withheld answers and the contribution of any single difficult question. Do not tune prompts or alter tools after seeing scored results to improve reported performance. If an implementation bug requires a correction, retain the affected data and document the version change and any separate rerun.

**Human review and ethics.** The primary study uses public secondary data and automated evaluation of structured outputs. No human participants are recruited by this implementation. A blinded review sheet is generated for optional auditing of free-form explanations; it contains no fabricated ratings. Any future human ratings require the student's applicable approval process. No inter-rater agreement or human reasoning score will be reported without genuine completed ratings. The student reports professor permission for AI assistance and satisfactory prior supervision/approval; the final declaration should reflect the actual assistance and applicable approval record.

**Freeze and reporting.** Before scored calls, save this protocol and a manifest containing dataset hash, exact prompts/questions, schema/tools, model settings, full scheduled plan, and source hashes. The manifest is a local pre-run record, not a claim of public preregistration. Every scheduled run, including failures, belongs in the reported denominator unless a clearly specified technical condition makes a particular metric unavailable. Preserve raw model outputs, tool receipts, cost ledger, completed results, analysis scripts, and a commit/release when the implementation is packaged. The offline notebook must reproduce all empirical tables from those records without API calls.
